# Project Context

> The stable, high-level context of the product: what it is, who it's for, its domains, its core entities, and its boundaries. Read it first so any change fits the product, not just the task.

---

## One-liner

**devkit** is the shared development toolkit of the droneey fleet: the configuration packages every TypeScript repository installs and the templates it copies once, so every repository lints, formats, type-checks, hooks, tests and orders its manifests the same way.

## Context & users

A fleet of repositories each carrying its own copy of every tool's configuration drifts: a rule fixed in one place is fixed nowhere else, and a new repository starts from whatever was copied last. devkit keeps one canonical configuration per tool, published as a package a repository extends in one line; a change to the kit is one release, and the dependency bot carries it to every consumer.

- **A repository of the fleet** installs the packages it needs, extends them and pins the kit through its lockfile; it owns its tools, the kit owns their configuration.
- **A repository without a package manager** takes the git hooks straight from the kit's common area, pinned to a release.
- **The constitution** names the kit in its stack chapters: the kit is the mechanics behind the rules, never the rules themselves.

## Domains

- **Lint and format** — the Biome configuration: a base, an environment, a framework, the tests.
- **Language** — the TypeScript configuration variants: base, node, browser, mobile.
- **Git hooks** — the branch and commit rules and the pre-commit lint, with the language-agnostic base in the common area.
- **Package manifests** — the Syncpack configuration: field order, ranges, formatting.
- **Tests** — the Jest presets for the repositories that test with Jest, and the Bun test template for the rest.
- **Templates** — the files no tool can extend: the editor configuration, the ignore lists, the lint of YAML, the scripts, the test runner configuration, the framework setup files.
- **Docker Compose** — a written convention on the order of keys in a compose file; a document, not a package.

## Core entities & relationships

- **Package** — `@droneey/devkit-ts-<name>`: one folder, one manifest, one README, one licence, its specs and a curated surface of exports. Every package carries the same version.
- **Entry** — one export a consumer extends; the manifest lists every entry and nothing else.
- **Peer** — the tool a package configures, declared with a version range and installed by the consumer.
- **Common file** — a language-agnostic source in the common area; a package ships a copy generated by its build, and a spec guards the copy.
- **Template** — a file copied once by a consumer and owned by it from then on; the kit never checks the copies.
- **Release** — one tag, one version written into every manifest, every public package published to the registry through the identity of the release workflow.
- **Consumer** — a repository that extends the kit: it takes an entry through its tool's own `extends`, a one-line module where the tool reads code, or the remote configuration where it has no package manager.

## Boundaries — what it does not do

- **Ships no product code.** A package holds configuration or tooling, never a business.
- **Owns no tool.** The consumer installs the tool; a package is its configuration and a runtime dependency exists only where the package executes code of its own.
- **Checks no copy.** A template is copied and forgotten; a file that would need a checker is an export instead.
- **Holds no rules and no workflows.** The rules are the constitution's; the reusable workflows, the Renovate preset and the contributing guide are the organisation's hub.
- **Knows no consumer.** No package carries a repository's name or a path into a repository.

## Non-functional notes

- **One version for all packages,** decided by the merged branch prefix and written by the release automation; a version already on the registry is a skip.
- **Publishing needs no token:** every package carries a trusted publisher for the release workflow; a new package is published once by hand first.
- **The kit dogfoods itself:** the root installs its own packages as workspace dependencies and extends them like any consumer.
- **A consumer follows the kit through its lockfile and the dependency bot;** nothing in the kit updates a consumer.
